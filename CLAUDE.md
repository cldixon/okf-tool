# CLAUDE.md

## Spec
The source of truth for Tempra's design, decisions and current state is the Tempra library
**`cl_dixon/tempra-dev`**, read and written over the Tempra MCP tools (`start` with
`library: "cl_dixon/tempra-dev"`). Its `guide.md` says what belongs there; `v2/` is the managed
service as built, `delivery/` is CI/CD, `decisions/` records why, `process/workflow.md` is how a
change goes from a Linear issue to production. Read the concepts a feature touches before starting
on it. When implementation shows a concept is wrong, update the concept first, then the code.

OKF semantics, the store, the ledger and the MCP tools are still specified in the v1 Claude Doc,
**OKF Knowledge Service — Spec** (https://claude.ai/artifact/KMuKyyFBSJHzukyEGqvUDn), until they are
carried over. The v2 Claude Doc is retired (carried over at rev 20). There is no markdown copy of
either in this repo; do not add one.

## UI
The app and the landing page share one design system, `design/` (`@tempra/design`, TEMPRA-8): tokens as CSS custom properties (`--tempra-*`, light and dark through `light-dark()`), a base stylesheet and `.prose` for rendered markdown. Edit `design/src/*.css`, then `bun run build` in `design/` to regenerate `design/dist/` (committed; a test fails if it is stale). The app's build writes it, with its fonts, into the Worker's static assets at a hashed path (`/_design/tempra.<hash>.css`, `style-src 'self'`; TEMPRA-174) and every page links it; the site imports `@tempra/design/tempra.css`. Visual changes go in the package, not in either consumer.

Minimal and barebones first, in the app and on the site (spec: tempra-dev `v2/design-system.md`, UI rule). This is about styling, not technology: light neutral surfaces, dark text, clear links, pill buttons for actions, no design flourish and no colour until the palette (TEMPRA-1), and as little text as works (headings, labels, links, short sentences), so the bones of what we build stay visible. Scripts, TypeScript, Svelte components and client-side state are fine where a page needs them; the app is a Svelte SPA (TEMPRA-9, TEMPRA-179). Every visual decision comes from `@tempra/design` (tokens, base CSS, and layout primitives and components as they are needed); neither consumer adds styling beyond its own page layout, and nothing is styled inline. The look comes from a separate design effort (TEMPRA-1) working in the package.

The app is a Svelte 5 SPA, `app/` (`@tempra/app`, TEMPRA-9, TEMPRA-14; React 19 until the port, TEMPRA-176 to 180, tempra-dev `decisions/web-app-svelte.md`, `app/svelte-port.md`): plain Svelte with runes, not SvelteKit (routing, auth and the shell stay in the Worker; `App.svelte` matches routes with `router.ts`); hooks are rune functions in `.svelte.ts` modules (`useLoad` in `load.svelte.ts`, the feed in `live.svelte.ts`, `here.url`, the page on screen, and `here.address`, where the browser is, in `location.svelte.ts`: a move to a page not in the cache keeps the page on screen until its data arrives or 300 ms pass, then it draws Loading…, `hold.ts`, TEMPRA-194) whose changing arguments are getters and whose results are read through getters, API data kept in `$state.raw`; components carry no `<style>`, no `style:` directives and no transitions; the runes' traps (tempra-dev `app/svelte-spike-live.md`): never destructure a hook's result or the frame (it freezes the value); an effect or derived that reads an object made afresh on every redraw (a derived returning a new `{…}`) runs again each time, so follow a string or the same object (`useLoad` and `useFeed` follow their key, not the `Urls`; `runes.test.ts` holds them to it); Svelte trims spaces at an element's edges where JSX kept them, so a leading or trailing space is written as an expression (`{" for "}`); a keyed `{#each}` throws on a duplicate key; `{@const}` is evaluated lazily, so read it before clearing what it reads; the account's and a library's settings pages are one chunk loaded on first use (`pages/settings.ts`). Every page (library list, directory, concept, attachment, activity, ledger, the library's settings, and the account's welcome, agents, invitations and account pages) is one shell from the Worker (`worker/src/ui/spa.ts`): the design stylesheet, the bundle at a hashed path (`/_app/app.<hash>.js`, immutable; code-split, so what only some pages need, Pele for diagrams, is a chunk beside it at `/_app/<name>-<hash>.js`, fetched on first use) and an empty root; the bundle, its chunks, the stylesheet, its fonts and `/favicon.svg` are Workers static assets (TEMPRA-174), which `app/build.ts` writes to `app/dist/public/` with a `_headers` file (immutable, `nosniff`) and Cloudflare serves before the Worker runs (`assetsDirectory` in `worker/wrangler.config.ts`, `assets` in `cloudflare.config.ts`), so they are not in the Worker's script and never count against a session; a name under `/_app/` or `/_design/` no build wrote reaches the Worker and is a plain 404; under a CSP of `script-src 'self'` and `style-src 'self'` (the nonce went with Wordgard, TEMPRA-99; the reader's popovers get their coordinates through the CSSOM, which CSP leaves alone); no inline scripts or styles. ## Tooling
- **bun for everything JS/TS**: installing (`bun install`, `bun add`), scripts (`bun run …`), tests (`bun test`), one-off binaries (`bunx`). Do not use npm, npx, yarn or pnpm, and do not commit other lockfiles.
- **TypeScript only** on the server (Worker + Durable Object). No Rust or WASM in v1.
- **Biome** for lint and format (`biome.json`); no ESLint or Prettier. In `.svelte` files Biome formats and lints the `<script>` blocks only (it cannot see uses in the markup, so its unused-variable, import-type, const and hook rules are off there); `svelte-check` (`bun run typecheck` in `app/`) checks them, with `--tsgo` (TypeScript 7; svelte-check needs TypeScript 6 beside it, `typescript@~6` and `@typescript/native` as app/ dev dependencies).
- **cf** (Cloudflare's CLI, beta, pinned) is a dev dependency of `worker/`; run it with `bunx cf …` from `worker/`. The Worker is configured in `worker/cloudflare.config.ts`; there is no `wrangler.jsonc`. To find a command, use `bunx cf cli search "<task>"` (anonymous wording: no names or IDs), then `--help` on the match or `bunx cf schema <command>`; do not walk nested `--help`. cf resource commands take IDs, not names or bindings (scripts/cf.ts reads the D1 ID from the config). Set `CF_SEND_TELEMETRY=false` in scripts and CI. Scripts call cf through `scripts/cf.ts` (async): cf (beta) sometimes prints its result and then never exits (a confirmation prompt keeps it alive, e.g. `d1 migrations apply`), so the helper accepts a complete JSON result once cf goes quiet, and otherwise times out and retries; keep calls made through it safe to repeat.
- **wrangler** stays a dev dependency only as the bundler `cf dev`/`cf build` delegate to (`worker/wrangler.config.ts`, which also names the static assets' directory, `assetsDirectory`, through `node_modules/@tempra/app` so the gate's copied project finds it too). Use Wrangler directly only for what cf lacks: live logs (`bunx wrangler tail tempra`).
- **The site is the exception:** `site/` is configured with `site/wrangler.jsonc`, because Cloudflare Workers Builds (which deploys it and posts PR previews) reads a Wrangler config. It has no bindings or data.

## Testing
- Unit tests run under `bun test`. `cloudflare:workers` does not exist outside workerd, so tests stub it with `mock.module` (see `worker/test/healthz.test.ts`).
- Keep storage and OKF logic free of Worker APIs so it can be tested under bun with `bun:sqlite` standing in for the DO's SQLite handle (`worker/test/sqlite.ts`).
- Bodies are normalized once on their way in, then byte-stable (tempra-dev: decisions/structured-documents). `editor/editor.test.ts` checks every concept body in `fixtures/`: normalizing twice changes nothing, the canonical form parses to the same tree, and the document's text has every textblock in place; plus raw constructs, link rules and the word diff. `editor/reconcile.test.ts` checks block IDs through edits, inserts, deletes, moves and the app's hints. `app/reader.test.ts` draws every fixture concept with the reader into a DOM (happy-dom, mounted with Svelte's `mount`): every textblock at its `docText` offset and reading as its text, every block ID drawn once, offsets through DOM points and back (atoms included), selections to the quotes anchors store, the diff leaving the counting alone; plus unsafe links, escaping, raw HTML as code, markers and headings. A failing fixture is a bug in the reader, not a fixture to skip. App tests run with `bun test --conditions browser` (the package's `test` script, so `svelte` resolves to its client runtime); `app/test/setup.ts`, preloaded by `app/bunfig.toml`, compiles `.svelte` and `.svelte.ts` files with `svelte/compiler` and installs one happy-dom window for the run (Svelte's runtime keeps the DOM accessors it first meets); `app/test/dom.ts` has `draw` and `settle`.

- The DO write transaction must stay synchronous (no awaits); hash with `okf/hash.ts`, not WebCrypto.
- The blob sweep: `worker/test/sweep.test.ts` (a world of libraries, a bucket and a queue drained into the consumer: the 31 days, the first count holding deletion, a library that never answered, restores, deletes, idempotent messages, the listing and the drift scan; and the write path recording uploads and references). `bun scripts/sweep-bench.ts [libraries]` times it at scale. Never delete a blob still referenced: anything unsure keeps the blob.

## Cloudflare
- `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` are set in the cloud environment; cf (and wrangler) read them automatically.
- Remote resources: Worker `tempra` on `app.tempra.dev` (custom domain; `workers.dev` is off), D1 `tempra-accounts` (id in `cloudflare.config.ts`), R2 bucket `tempra-blobs`, KV `tempra-oauth`, Queue `tempra-sweep` (binding `SWEEP_QUEUE`, the blob sweep's fan-out, sent and consumed by the Worker; no dead-letter queue, TEMPRA-81), Queue `tempra-agent` (binding `AGENT_QUEUE`, the managed agent's turns, TEMPRA-222; staging `tempra-agent-staging`), Queue `tempra-mail` (binding `MAIL_QUEUE`, outgoing mail with retries, TEMPRA-89; staging `tempra-mail-staging`, previews `tempra-mail-pr-N`; no dead-letter queue), all, like `tempra-sweep`, created by `bun run deploy` when missing, from the bindings in `cloudflare.config.ts`. Do not create or delete remote resources without asking.
- `ANTHROPIC_API_KEY` (the managed agent's model) is a Worker secret: the staging and production deploy jobs set it from the GitHub secret of the same name through Cloudflare's API (`worker/scripts/worker-secret.ts`, skipped when the secret is empty); previews get it from `preview up`.
- Tokens and libraries are managed at `/agents` and `/` (or `/api/v1/tokens` and `/api/v1/libraries` with a `human:` token). `bun run seed --remote` (from `worker/`) still creates a library and token directly in the deployed D1.
- D1 read replication (TEMPRA-85, tempra-dev `v2/read-replication.md`): every request runs its D1 queries in one Sessions API session (`withD1Session` in `worker/src/d1session.ts`, held in an AsyncLocalStorage; the Worker's D1 handles are `routedDb(env.DB)`, which use the binding outside a request: crons, queues, the DO). A browser's `GET`/`HEAD` starts at the bookmark in its `__Host-tempra_d1` cookie, else `first-unconstrained`; any other method, and any request with `Authorization`, starts `first-primary`; a browser's write gets the session's bookmark back in that cookie when it is newer. Correct with replication on or off; whether a database replicates is `readReplication` in its deployment in `cloudflare.config.ts` (`auto` for production and staging, unset for previews), which `bun run deploy` applies when it differs (`ensureReadReplication` in `scripts/cf.ts`, through `cf d1 edit --read-replication-mode`). `worker/test/d1.ts` has a `withSession` without replicas; `worker/test/d1session.test.ts` runs one with a lagging replica.
- KV `tempra-oauth` (binding `OAUTH_KV`) holds OAuth clients and grants. The UI signs people in by email link only (Access was removed at the A4 cut-over); `SIGNUP` (a config var: `invite` in production and staging) decides who may create an account, and `bun run admin invite` manages the list. Local dev uses `DEV_SIGNIN=1` and `SIGNUP=open` from `worker/.dev.vars` (copy `worker/.dev.vars.sample`): sign-in links show on the page for localhost.
- `cloudflare.config.ts` is a function of `--mode`: production by default, `staging` for a separate Worker (`tempra-staging` on `staging.tempra.dev`) with its own D1 `tempra-accounts-staging`, R2 `tempra-blobs-staging`, KV `tempra-oauth-staging`, Queue `tempra-sweep-staging`, metering to `tempra_usage_staging` and rate-limit namespaces 2001, 2002 and 2003 (TEMPRA-76), and `preview` for PR N (`previewDeployment`: `tempra-pr-N` on `pr-N.tempra.dev` with `-pr-N` resources (Queue `tempra-sweep-pr-N` too), ids from `TEMPRA_PR`, `TEMPRA_PREVIEW_D1_ID`, `TEMPRA_PREVIEW_KV_ID`; no cron; metering to `tempra_usage_preview`, rate-limit namespaces 3001, 3002 and 3003). Scripts pick the mode from `TEMPRA_MODE`. With no mode (`cf dev`, `cf workers types`, a bare dry run) no custom domain is attached; `bun run deploy` defaults to `--mode production`.
- Mail goes through Cloudflare Email Service: the `EMAIL` binding is added only when `mailFrom` is set for a deployment in `cloudflare.config.ts`, which needs a sending domain onboarded in Cloudflare. Production sends from `noreply@mail.tempra.dev` (`mail.tempra.dev` is onboarded); local dev with `DEV_SIGNIN=1` still shows links on the page instead of mailing them. Incoming mail is Cloudflare Email Routing on the `tempra.dev` zone, from `inboundMail` in production's deployment in `cloudflare.config.ts`: `hello@tempra.dev` (the landing page's contact) forwards to `"operator"`, the address in `OPERATOR_EMAIL` when `bun run deploy` runs (CI passes the `PREVIEW_EMAIL` secret), so no personal address is in the repository; `ensureEmailRouting` in `scripts/cf.ts` enables routing, registers the destination (Cloudflare mails it a verification link once, and refuses a rule to it until that is clicked, so the rule comes on the next deploy after) and creates or corrects each rule, never deleting one it does not manage, and only warns if it cannot. `OPERATOR_EMAIL` (a Worker secret, so the address stays out of the repo) receives the daily digest and a notice when someone new joins the waitlist (at most 10 a day), and is the only account that can open `/waitlist` to approve or dismiss them.
- Rate limits are `WRITE_LIMITER` (60 writes a minute per account), `REQUEST_LIMITER` (600 requests a minute per token or app) and `SESSION_LIMITER` (`SESSION_REQUESTS_PER_MINUTE` in `cloudflare.config.ts` per browser session, keyed by the session's stored hash: every page, API call and feed upgrade made with the cookie and no token, static files aside; TEMPRA-80; the gate fails if a busy browse uses over a quarter of it), production's on namespaces 1001, 1002 and 1003 (namespaces are account-wide, so each deployment has its own; `worker/test/config.test.ts` checks none is shared). Over a limit is a 429 with `Retry-After`; the SPA waits it out quietly (`api.ts`: reads retry, prefetches skip, what is shown stays); metering writes to the Analytics Engine dataset `tempra_usage`; storage per library is `LIBRARY_STORAGE_MB`.
- What each call costs (TEMPRA-228, tempra-dev `v2/operation-costs.md`): the Library DO counts each statement's `rowsRead`/`rowsWritten` (`RowTally` in `store/sql.ts`), returns them on `CallResult.cost`, and the Worker meters one `cost` point per MCP tool call and REST request under its name (`worker/src/op-costs.ts`; `costs.ts` is the price table and cost report); a request sent with `X-Tempra-Cost: 1` gets its cost back in an `X-Tempra-Cost` JSON header (totals and each DO call).
- The landing page is the Worker `tempra-site` on `tempra.dev` and `www.tempra.dev` (www redirects to the apex). Cloudflare Workers Builds, connected to this repository with root directory `site`, deploys it: `main` runs `wrangler deploy`, other branches run `wrangler preview`, which posts a Preview URL and one per commit on the PR. It does not go through the app's preview/staging/production jobs.
- Naming: the product is Tempra (repository `cldixon/tempra`, `tempra.dev`); OKF names only the file format. The former `okf-service` Workers and their resources were moved and deleted (v2 spec: Move to tempra.dev). Don't introduce `okf-tool`/`okf-service` names.
- `worker/` is the deployable project and must stay self-contained: its own `package.json` with every dependency, nothing imported from outside `worker/` at build time except the `@tempra/design`, `@tempra/app` and `@tempra/editor` workspace packages (the Worker imports only `@tempra/editor/doc`) (CI's standalone job builds `worker/` with `design/`, `editor/` and `app/` alone; `bun install` builds the app's bundle). Nothing in the repository imports Wordgard any more (TEMPRA-99). `site/` takes the same package as `file:../design`, so Workers Builds must watch `design/*` as well as `site/*`. `cloudflare.config.ts` must not import Worker code (scripts import it under bun).

## CI
`.github/workflows/ci.yml` runs on PRs and pushes to `main`: `bun run check`, `bun run gate` (cf dev, sample-bundle round-trip, UI pages, the SPA and its reader in Chromium, MCP smoke), and a standalone build of `worker/` copied with `design/`, `editor/` and `app/` (`cf deploy --dry-run`). All must pass before merging.

CD (tempra-dev: `delivery/ci-cd.md`) runs after those three, each stage off until its repository variable is `on`:
- `PREVIEWS`: the `preview` job brings up PR N's preview and comments its URL; `preview-cleanup.yml` tears it down when the PR closes and sweeps leftovers nightly.
- `STAGING_DEPLOYS`: every push to `main` deploys staging and checks it (`/healthz`, MCP smoke with secret `STAGING_MCP_TOKEN` if set).
- `PRODUCTION_DEPLOYS`: then production in the same run, with no approval step (tempra-dev: `decisions/production-without-approval.md`); the GitHub Environment `production` has no required reviewer, and adding one would bring the step back.
- Each push to `main` runs on its own (TEMPRA-18): one run never blocks the next, and deploy jobs deploy only the tip of `main` (a superseded commit skips itself).

The `site/ builds` job checks, tests and builds the landing page; its previews and deploys come from Workers Builds.

Secrets: `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `PREVIEW_EMAIL` (the operator, seeded as each preview's account, and the production deploy's `OPERATOR_EMAIL`, where `hello@tempra.dev` forwards), optional `STAGING_MCP_TOKEN`, `PRODUCTION_MCP_TOKEN` (read-only smoke), optional `ANTHROPIC_API_KEY` (only the preview job's `preview up` step sees it, and sets it on the `tempra-pr-N` Worker as a secret through Cloudflare's API; the managed-agent spike, TEMPRA-67), optional `PREVIEW_SEED_TOKEN` (a read-only token on the seed library, only for the `preview up` step, with repository variables `PREVIEW_SEED_LIBRARY` and optional `PREVIEW_SEED_URL`; TEMPRA-109).
